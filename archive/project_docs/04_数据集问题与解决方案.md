# 数据集问题深度反思与解决方案

## 当前数据集（final版本）的3个严重问题

### 问题1：负样本污染（假负样本）

**问题描述**：
我们的负样本是从参考基因组中**随机截取**的DNA片段。但Streptomyces基因组平均包含20-30个BGC，总BGC区域约占基因组的7-10%。随机截取的话，约7-10%的"负样本"实际上落在了BGC区域内——它们是假负样本。

**影响**：
- 约935-1336个假负样本（占负样本的4-6%）
- 模型在这些样本上会收到错误的梯度信号
- 会降低模型的精确率（把真BGC判为非BGC）

**解决方案**：
1. **最佳方案**：先用antiSMASH/BGC-Prophet标注参考基因组中的BGC区域，然后排除这些区域再采样
2. **折中方案**：使用BGC-Prophet的85KG预测结果。85KG数据告诉我们每个基因组哪些窗口被预测为BGC，我们可以只从NonBGC窗口对应的区域采样
3. **最简方案**：接受少量假负样本的噪音。深度学习模型对少量标签噪音有一定鲁棒性。但需要在论文中承认这个limitation

### 问题2：正负样本物种分布不匹配

**问题描述**：
- 正样本39%来自"unknown"属（MIBiG中很多BGC缺少物种注释）
- 负样本60%来自Streptomyces

模型可能学到"Streptomyces的一般DNA特征 = 非BGC"，而不是真正的BGC vs non-BGC差异。

**影响**：
- 在Streptomyces以外的物种上，模型表现可能大幅下降
- RF AUROC=0.95中有一部分可能来自这种物种偏差

**解决方案**：
1. **最佳方案**：对每个BGC，找到其来源物种的完整基因组，从同一基因组中采负样本。这是BGC-Prophet的做法
2. **折中方案**：按正样本的物种分布来调整负样本的采样权重。如果正样本30%来自Streptomyces，负样本也应该30%来自Streptomyces
3. **评估方案**：构建按物种分层的测试集，分别评估在不同属上的性能

### 问题3：物种级别数据泄露

**问题描述**：
MIBiG中502个BGC来自Streptomyces，我们的负样本也来自197个Streptomyces基因组。如果某个BGC恰好来自我们下载的参考基因组的同一个菌株，同一段DNA可能同时出现在正样本和负样本中。

**影响**：
- 评估指标虚高
- 模型泛化能力被高估

**解决方案**：
1. 交叉检查MIBiG BGC的来源菌株与参考基因组列表，排除重叠
2. 在数据分割时按物种/属分组，确保同一属的样本不同时出现在训练集和测试集中

## BGC-Prophet是怎么解决这些问题的？

回头看论文，BGC-Prophet的数据构造策略其实非常精巧：

```
1. 从MIBiG获取2502个BGC（正样本的"核心"）
2. 用antiSMASH在6KG数据集(5886个基因组)上预测BGC
3. 在每个基因组中，去掉被antiSMASH预测为BGC的区域
4. 剩余区域中的基因作为non-BGC基因库
5. 对每个MIBiG BGC：
   - 取BGC中的基因作为正样本核心
   - 从non-BGC基因库中随机取基因填充两侧（padding）
   - 每个BGC重复5次，每次用不同基因组的基因做padding
6. 负样本：从non-BGC基因库中取128个连续基因
```

这个策略同时解决了上述三个问题：
- 负样本来自已确认不含BGC的区域（解决问题1）
- 正负样本的基因来自相同的基因组池（解决问题2）
- 通过数据增强（不同基因组的padding），增加多样性

**但这个策略对我们有一个关键困难**：它在基因级别操作（每个样本是128个基因ID），而我们在DNA级别操作。我们需要设计等价的DNA级策略。

## 我们的DNA级解决方案

### 策略：从同一基因组中同时取正负样本

```
1. 选择一批完整基因组（我们已下载的306个）
2. 用antiSMASH标注每个基因组中的BGC区域
   - 或者：使用85KG中对应基因组的BGC-Prophet预测结果
3. 正样本：BGC区域的DNA片段
4. 负样本：同一基因组中非BGC区域的DNA片段
5. 数据增强：对MIBiG BGC，替换flanking区域为不同基因组的对应区域
```

### 但等一下——用antiSMASH/BGC-Prophet标注的结果作为"真实标签"合理吗？

这涉及到一个深层问题：

- 如果我们用antiSMASH来标注训练数据 → 我们的模型最多只能学到antiSMASH能检测到的BGC
- 老师的目标是发现**非典型BGC**（antiSMASH检测不到的）
- 这形成了一个矛盾

**解决思路**：
- 正样本仍然只用MIBiG（实验验证的真实BGC，不依赖antiSMASH）
- 负样本用antiSMASH标注来**排除已知BGC区域**
- 这样我们的模型学到的是"已知BGC vs 确认的非BGC"
- 对于非典型BGC，模型可能会给出中等置信度——这正是我们想要的探索空间

## NVIDIA NIM API 发现

### Evo2 40B Forward API 可以提取embedding！

```
Endpoint: https://api.nvcf.nvidia.com/v2/nvcf/pexec/functions/475da3a9-515e-417e-8c4d-f847c271d2be
Method: POST
Payload: {"sequence": "ATGC...", "output_layers": ["blocks.20.mlp.l3"]}
返回: base64编码的numpy数组, shape=(1, seq_len, 8192)
```

### 层选择测试结果

| 层 | |mean| | 范围 | 状态 |
|---|---|---|---|
| blocks.0 | 0.002 | [-0.09, 0.07] | 太浅，信号弱 |
| blocks.10 | 0.036 | [-9.1, 11.4] | 有信号 |
| blocks.20 | 1.826 | [-44.8, 24.3] | **最佳** |
| blocks.28+ | ~0 | 全是0 | 可能是精度问题 |
| unembed | 23.7 | [-27.1, 2.3] | logits层(512维) |

**blocks.20.mlp.l3 是当前最佳选择**：值有意义且变化大。

## Evo2 40B 最小可行性实验结果（100个样本，5折交叉验证）

| 特征 | LR AUROC | RF AUROC |
|---|---|---|
| Evo2 unembed (512维) | **0.704 ± 0.056** | 0.596 ± 0.082 |
| k-mer (260维) | 0.582 ± 0.143 | 0.739 ± 0.068 |
| Evo2 + k-mer合并 (772维) | 0.710 ± 0.059 | **0.798 ± 0.096** |

### 关键解读

1. **Evo2 unembed embedding确实携带了BGC相关信息**：LR AUROC=0.70 > k-mer的0.58
2. **但unembed层不是最佳层**：unembed是logits层(预测下一个碱基的概率分布)，不是最好的特征表示层
3. **合并特征效果最好(0.80)**：说明Evo2和k-mer捕捉了不同维度的信息
4. **RF在Evo2上表现差(0.60)**：可能因为样本太少(100个)RF过拟合，或者512维的unembed空间不适合RF
5. **这只是unembed层的结果**：blocks.20层有8192维的embedding，信息量远大于unembed的512维，但通过API传输不实际

### 这意味着什么

- **方案可行**：即使用最不理想的unembed层+简单均值池化，Evo2也能提供有用信号
- **需要GPU**：要用blocks.20层（真正的embedding层），必须在GPU上本地运行
- **需要更好的数据**：100个样本太少，且数据集有前述的3个问题
- **合并特征是个好方向**：Evo2 embedding + 传统特征互补
